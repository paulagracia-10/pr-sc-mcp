# Live Validation Runner

This folder contains the runner and instructions for the Live Validation stage of the PR-SC MCP study.

## Purpose

The Live Validation stage evaluates whether PR-SC MCP remains effective when the final answer is generated by live LLM inference rather than deterministic architecture-internal scoring.

The final study evaluates three open-weight models served through Cerebras infrastructure:

- `gpt-oss-120b`
- `gemma-4-31b`
- `zai-glm-4.7`

The evaluation matrix is:

```text
10 case families × 4 architecture variants × 5 repeated runs per model
```

Across three models, this yields:

```text
600 generated answers
```

## Runner

```text
v5_1_cerebras_subset_runner_v1.py
```

This runner implements the Live Validation stage. It constructs controlled prompts, applies architecture-variant logic, calls the selected model through the Cerebras OpenAI-compatible API, records telemetry, applies deterministic post-checks, and exports per-run and per-variant results.

## Architecture variants in Live Validation

The Live Validation stage uses four variants:

1. `Exhaustive MCP Baseline`
2. `Routing MCP`
3. `Routing + Packaging, no compression`
4. `Full PR-SC MCP`

Earlier internal files may refer to `Naive MCP`. In the final paper, this corresponds to `Exhaustive MCP Baseline`.

Use `.env.example` as a safe template.

## Outputs

Each run batch produces three main output types:

```text
*_run_summary*.csv
*_run_records*.json
*_summary_by_variant*.csv
```

### `run_summary` CSV

Contains one row per generated answer, including fields such as:

- case ID;
- case family;
- architecture variant;
- model;
- latency;
- prompt tokens;
- completion tokens;
- total tokens;
- deterministic quality checks;
- generated answer.

### `run_records` JSON

Contains the fuller record for each generation. This is the best source for auditability, answer inspection, and semantic review sampling.

### `summary_by_variant` CSV

Aggregates results by architecture variant for a run batch.

## Notes on token accounting

The paper reports total-token telemetry for Live Validation. Total tokens include:

```text
prompt tokens + completion tokens
```

Prompt tokens reflect the architecture-controlled context burden. Completion tokens reflect model-specific generation behavior.

## Notes on deterministic decoding

The runner uses deterministic decoding with `temperature = 0.0`. However, deterministic decoding does not guarantee that every model will produce identical completion lengths across repeated runs. In the final results, `gemma-4-31b` showed invariant token counts across repeated runs, while `gpt-oss-120b` and `zai-glm-4.7` showed non-zero token variability.
